## 📌 Problem Statement

During road accidents, fires, floods, building collapses and other disasters, coordinating the emergency response becomes extremely difficult. Reports arrive from many sources at once, and controllers must decide in seconds which incident is most critical and which team should respond. Existing workflows suffer from three fundamental bottlenecks:

1. **Scattered Reports, No Central View:** Calls, messages and walk-in reports arrive through different channels. Without one place that collects them, critical incidents are missed or duplicated, and administrators cannot see the whole situation.
2. **Subjective Prioritisation:** Deciding which emergency comes first is often done by gut feeling. A fire with 20 trapped people and a minor road accident can sit in the same queue, and the time an incident has already been waiting is rarely taken into account.
3. **Slow, Manual Team Dispatch:** Finding the closest free team that has the right skills (fire, medical or rescue) is done by phone or memory. Teams are double-booked, left idle, or sent from across the city while a closer unit is available.

**ResQLink** addresses this with a single web platform. Users submit structured emergency reports, the system **classifies severity automatically**, **ranks every open incident by a priority score**, and **assigns the nearest available, suitable response team** using real distance calculation. Administrators track each incident through its full lifecycle on a live dashboard and map.

## 🚀 Features

### Round 1 – Emergency Incident Reporting & Monitoring

| Feature | Module | Mechanism | Output | Status |
|---|---|---|---|---|
| **Emergency Reporting Form** | `report()` / `sub()` | Validated form capturing title, description, category, location, people affected and optional contact. | A stored incident record with a unique ID and timestamp. | **Complete** |
| **Six Emergency Categories** | `CATS` | Fire, Road Accident, Medical, Flood, Building Collapse, Other, each with an icon, a risk weight and a list of suitable team types. | Every incident is tagged and routed by category. | **Complete** |
| **Automatic Severity Classification** | `classify()` | Rule-based score from category weight, people affected and emergency keywords in the text. | Low / Medium / High / Critical level on every report. | **Complete** |
| **Emergency Dashboard** | `dash()` | Live aggregation of all incidents. | Total, critical, pending and resolved counts plus incidents by category. | **Complete** |
| **Incident Management** | `list()` / `setStatus()` / `del()` | Filterable incident list with status dropdown and delete action. | Administrators view, update and remove reports. | **Complete** |
| **Professional, Responsive UI** | CSS | Mobile-first grid layout, light and dark themes, pulsing highlight on Critical incidents. | Readable on phones, tablets and desktops. | **Complete** |

### Round 2 – Intelligent Emergency Coordination

| Feature | Module | Mechanism | Output | Status |
|---|---|---|---|---|
| **Intelligent Incident Prioritisation** | `prio()` | Composite score of severity, people affected, time since reporting and category weight. | Ranked priority queue with a numeric score on each card. | **Complete** |
| **Response Team Management** | `teams()` / `addT()` / `tog()` | Create teams with ID, name, category (Fire / Medical / Rescue), coordinates, availability and assigned incident. | Editable fleet of response teams. | **Complete** |
| **Location-Based Team Assignment** | `dist()` / `assign()` | Haversine great-circle distance between each team and the incident; filters by availability and suitability. | Nearest suitable team assigned automatically. | **Complete** |
| **Assignment & Incident Tracking** | `setStatus()` | Lifecycle: Reported, Pending, Assigned, In Progress, Resolved. Teams switch to busy on assignment and free on resolution. | Assigned team details shown on each incident. | **Complete** |
| **Route & Location Visualisation** | `map()` | SVG map plots incidents (colour-coded by severity) and teams, with dashed route lines and distance labels. | Visual overview of the response situation. | **Complete** |
| **Advanced Analytics Dashboard** | `dash()` | Extended statistics. | Available and busy teams, assigned and resolved incidents, severity mix, category distribution. | **Complete** |

### 1. Severity Classification

severity_score = category_weight + people_bonus + (1.5 × keyword_matches)

Code snippet

| Category | Weight | | People Affected | Bonus |
|---|---|---|---|---|
| Fire Emergency | 3.0 | | 20 or more | +3 |
| Building Collapse | 3.0 | | 5 to 19 | +2 |
| Medical Emergency | 2.5 | | 1 to 4 | +1 |
| Flood | 2.5 | | 0 | 0 |
| Road Accident | 2.0 | | | |
| Other Emergency | 1.0 | | | |[cite: 1]

**Keywords:** `trapped`, `explosion`, `fatal`, `dead`, `unconscious`, `bleeding`, `collapse`, `children`, `spreading`, `gas`, `drowning`[cite: 1]

| Score | Severity |
|---|---|
| 8 or above | 🔴 Critical |
| 6 to 7.9 | 🟠 High |
| 4 to 5.9 | 🟡 Medium |
| Below 4 | 🟢 Low |[cite: 1]

### 2. Priority Score

priority = (severity_level × 25)
+ (min(people, 50) × 0.8)
+ min(minutes_since_report × 0.5, 30)
+ (category_weight × 3)

Code snippet

Severity level is Low = 1, Medium = 2, High = 3, Critical = 4. The waiting-time term is capped at 30, so an old minor incident can never outrank a fresh critical one, but a neglected incident steadily climbs the queue.

### 3. Nearest-Team Assignment

| Incident Category | Suitable Teams |
|---|---|
| Fire Emergency | Fire |
| Road Accident | Medical, Rescue |
| Medical Emergency | Medical |
| Flood | Rescue |
| Building Collapse | Rescue, Fire |
| Other Emergency | Fire, Medical, Rescue |[cite: 1]

Distance is calculated with the **Haversine formula**:

a = sin²(Δlat / 2) + cos(lat₁) · cos(lat₂) · sin²(Δlng / 2)
distance = 2 · R · asin(√a)        where R = 6371 km

Code snippet

The available, suitable team with the smallest distance is assigned. **Auto-dispatch all** processes every unassigned open incident in priority order, so the most urgent incident gets the closest team first.

### 4. Lifecycle & Team Availability

| Event | Incident Status | Team Status |
|---|---|---|
| Report submitted | Reported | n/a |
| Team assigned | Assigned | Busy |
| Team arrives and works | In Progress | Busy |
| Incident resolved | Resolved | Available |
| Report deleted | Removed | Available (if assigned) |[cite: 1]
